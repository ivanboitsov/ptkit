# ADR 0001. Источники API MaxPatrol VM для ptkit 0.1

- Статус: принято
- Дата: 2026-10-13

## Контекст

Проект ptkit (docs/design.md) исходил из того, что в MaxPatrol VM выпускается
долгоживущий токен доступа, а PDQL-запрос сразу возвращает строки. Сверка со справкой
MaxPatrol VM 2.7 («Справочник разработчика -> Виды запросов к API», «Справочник по языку
запросов PDQL») показала другое.

1. **Авторизация.** В справке описано только получение токена по OAuth 2.0
   (`POST <адрес>:3334/connect/token`, `grant_type=password`, `client_id=mpx`, `client_secret`
   из конфигурации ядра); в примере ответа `expires_in: 86400`. На практике администратор
   выпускает токен для сервисной учётной записи в интерфейсе PT MC на длительный срок
   (например, на год). Этот способ в справочнике разработчика не описан.
2. **PDQL.** Документирован только первый шаг: `POST /api/assets_temporal_readmodel/v1/assets_grid`
   возвращает PDQL-токен (действует 30 минут). Для результата документирована только
   выгрузка всей таблицы в CSV (`GET .../assets_grid/export`). Постраничного JSON в справке нет.
3. **Версия сервера.** Эндпоинта нет в справке.
4. **Актив по идентификатору, группа по идентификатору.** Отдельных документированных
   эндпоинтов нет. Для групп есть дерево `GET .../v2/groups/hierarchy`.
5. **Задачи.** Есть контракты v3 и v4. В v4 список задач читается через POST с телом-фильтром.
6. **Экранирование строк в PDQL** в справке VM не описано.

Публичного стенда MaxPatrol нет, поэтому проверить поведение сервера при разработке нельзя.

## Решение

1. **Два способа авторизации.**
   - `Client(url, token=...)` — основной способ, как в проекте: токен, выпущенный в
     интерфейсе PT MC. Библиотека передаёт его в каждом запросе и не обновляет.
   - `Client(url, username=..., password=..., client_secret=...)` — запасной способ для
     инсталляций, где долгоживущий токен выпустить нельзя. Клиент сам получает токен
     в `/connect/token`, получает новый незадолго до истечения срока и один раз
     повторяет запрос после ответа 401.

   Неверный пароль даёт одну попытку входа, без повторов: так клиент не приближает
   блокировку учётной записи.
2. **Недокументированные эндпоинты.** Используются только там, где без них не выполнить
   требования проекта:
   - `GET /api/assets_temporal_readmodel/v1/assets_grid/data?pdqlToken=&offset=&limit=` ->
     `{"records": [...]}`: постраничная выдача строк PDQL;
   - `GET /api/deployment_configuration/v1/system_info` -> `{"productVersion": ...}`: `version()`.

   Оба эндпоинта вызывает веб-интерфейс MaxPatrol. Их показывают открытые материалы:
   рабочее пространство Nightingale к вебинару PT «How to use MaxPatrol VM API»
   (github.com/Reddoks/maxpatrol_api_nightingale, помечены как недокументированные) и
   Positive CLI (github.com/Reddoks/positive_cli). Адреса и разбор ответов есть только
   в `ptkit/vm/_compat.py`, рядом с пометкой «не документирован».
3. **Задачи читаются по контракту v3** (`GET /api/scanning/v3/scanner_tasks`,
   `GET .../{id}`), история запусков — `GET /api/scanning/v2/scanner_tasks/{id}/runs`.
   Все эти эндпоинты описаны в справке. Список v4 требует POST с телом-фильтром, у
   которого в справке противоречивые обязательные поля.
4. **`groups.get(id)`** ищет группу в документированном дереве `groups/hierarchy`.
   Недокументированный `GET .../v2/groups/{id}` не используется.
5. **`assets.get(id)`** выполняет PDQL `filter(Host.@Id = <uuid>) | select(...) | limit(1)`
   (псевдоним `@ID` документирован) и проверяет, что вернулся актив с тем же
   идентификатором.
6. **Экранирование.** Строка заключается в кавычки того вида, которого в ней нет.
   Обратная косая черта удваивается: так она записана в примерах PDQL в справке
   MaxPatrol SIEM (`"C:\\ProgramData"`). Строки с обоими видами кавычек и
   с управляющими символами отклоняются (`ValueError`). Значения без кавычек (UUID, IP,
   подсеть, дата, число) берутся только из типизированных объектов Python. Имена полей
   проверяются регулярным выражением. Поэтому пользовательский ввод не может изменить
   структуру запроса.

## Последствия

- Обновление MaxPatrol может сломать недокументированные эндпоинты. Ремонт — правка
  `_compat.py` и фикстур, остальной код не меняется.
- Ответы в `tests/fixtures/2.7/` собраны по справке, а не записаны с сервера.
  Unit-тесты проверяют логику библиотеки, но не формат реального сервера. Первый
  прогон `tests/live` на MaxPatrol VM 2.7 обязателен до объявления совместимости.
- `_compat.TESTED_VERSIONS` пуст: `productVersion` возвращает версию ядра MaxPatrol 10,
  а соответствия «VM 2.7 -> ядро» в справке нет. До первого живого прогона клиент
  предупреждает о непроверенной версии при каждом подключении.
- Запросы `POST .../assets_grid` и `POST .../connect/token` не меняют данные MaxPatrol.
  Принцип «только чтение» сохраняется.

## Что проверить на живом сервере

- [ ] `assets_grid/data`: формат `records`, ключи колонок (как в запросе или нормализованы).
- [ ] Ограничение группой через `additionalFilterParameters.groupIds` (или нужен `selectedGroupIds`).
- [ ] Литерал времени без кавычек (`Host.@UpdateTime > 2026-01-01T00:00:00`).
- [ ] `Host.@Name`, `Host.@Id` в `select` и `sort`.
- [ ] Значение `productVersion` для MaxPatrol VM 2.7 -> `TESTED_VERSIONS`.
- [ ] Формат тела ошибки 400 у `assets_grid` (текст для `PDQLError.message`).
